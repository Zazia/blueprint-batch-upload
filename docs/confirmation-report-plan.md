# 完成上传确认与操作报告：修改方案

日期：2026-10-27。用户授权：先做好方案，再交子 agent 实施两个优先项；同时全部流程图竖向，并配套讲清阶段逻辑。此方案补充原 v0.3，不改原冻结设计。图纸前置处理和变更动作识别仍只预留接口。

## 1. 需求与范围

1. 普通“上传 xx 路径”只授权文件上传；点击“完成上传”须明确授权或上传后确认。授权限于具体任务范围，不能由一个普通布尔值推断。
2. 报告说明本次具体动作、专业分布、材料处理、逐项结果、缺件和提交状态；支持一个项目多个单体/专业计划的汇总。
3. 介绍里的所有流程图使用从上到下方向。每图配套阶段说明，写明输入、目的、分支条件、输出或停止条件；纯图形方向改变不算完成。
4. 不操作生产系统；不修改真实图纸；不实现两个预留接口。原已验证的上传、解压与恢复经验保持。

## 2. 优先项 A：明确授权才可提交

### 决策逻辑

第一阶段，规划文件工作和任务限制：检查/试传/部分上传/先不提交按用户限制执行；普通完整文件上传不自动获准点按钮。

第二阶段，记录真实授权：明确的事前授权或事后确认均可，记录用户原话或可信证据引用、范围和批次。没有授权时只输出待确认，不制造默认许可。旧计划只有 completeRequested=true 也不能自动通行。

第三阶段，提交前检查：验证授权匹配当前范围、计划项已核实、必要材料齐全、快照完整、竣工必传集合满足。授权不能消除缺件或未知结果。按钮覆盖多个专业时必须核对全部范围，不拿单计划检查代表整个工程；文档应明确本地检查的范围限制。

第四阶段，浏览器执行与事后记录：代理按检查结论和真实按钮范围行动；回执只记录已发生结果。finalize 仍拒绝缺授权/缺件/错误范围，不把事后写回执当作提交前控制的替代。

### 实现约束

- 本地工具提供明确的授权记录和提交前检查入口，具体字段在操作参考中写全；不伪装成能验证人的真实意图的自动授权系统。
- 兼容读取旧计划，缺授权按待确认处理；显式试传或部分范围限制不能被默认值绕过。
- 操作参考、SKILL.md、README 统一新规则。历史设计保留，由本方案与当前执行文档承接。

## 3. 优先项 B：按真实操作汇总报告

### 统计与内容

- 已核实的正常图纸按原图新版、新增分类；按专业合计应与正常图纸总数一致。
- 目录、取消单、其他材料独立计数。一份取消单对应多个目标时区分源材料文件数与关联目标数；重试不重复增加图纸数。
- 本次上传与 reuseVerifiedFrom 的此前已成功项分开；系统原有已满足项不能无依据算进本次成功。
- 每项保留单体、专业、原文件/上传名、图号/图名、动作、结果、实际版本或证据引用；失败/缺件/未知单列，完整列表可读。
- 明确节点尚待确认、按限制未提交、提交条件受阻或已提交成功；目录未更新要具体提醒，区分初次建议与增补/取消必须补齐。
- 保留现有 JSON 字段供调用者使用；增加用户可读 Markdown 输出。多计划汇总显式指定范围，对重复或重叠计划不得静默累加。

### 能力边界

报告基于已记录事实，不读服务器、不猜专业或验证证据真伪。多个专业若分别记录在不同计划，必须真正读取这些计划再聚合，不能只把单专业的计数改个标题。尚未记录的材料不能写成上传完成。
