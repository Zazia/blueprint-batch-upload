# 需求与现状分析

日期：2026-10-09。状态：设计输入已整理，尚未实施。资料编号见 [资料索引](sources.md)。

## 1. 要解决的问题

用户面对的是不同阶段、角色和材料类型的图纸管理任务。上传文件只是其中一个动作。技能应先判断本次要完成哪项业务，再确定文件集合、目标记录、上传方法和完成条件。现有技能积累了真实操作经验，适合作为底层上传能力的起点，但不足以覆盖全过程任务。

本轮交付：本地 Git 仓库和基线、资料调研、现状与缺口、可评审设计、后续任务及计划。明确不修改原始技能正文、参考文件和脚本，也不试传真实图纸。

## 2. 当前能力盘点

| 能力 | 当前实际内容 | 完整程度 |
|---|---|---|
| 读取图纸清单 | DOM 导出 TSV；接收服务保存页面/API JSON | 有操作说明与接收脚本；缺统一数据结构、上下文和完整性校验 |
| 文件与图号对齐 | 精确图号、图名、相似度阈值 0.75 的策略；干跑后改名 | 指南，未提供可复用匹配和改名脚本；没有复核持久化 |
| 原生批量上传 | 人工多选无点图号文件，依赖系统自动匹配 | 有历史成功经验；匹配条件及当前工具能力需验证 |
| 逐条上传新版 | CORS 服务取文件、JS 调 `_saveAndupload`，修复 DOM/jQuery 问题 | 可复制代码；只按图号取首个目标，辅助函数固定 `.pack` |
| 分段执行 | 浏览器内循环，15–20 个一组，`window.__batchStatus` 记进度 | 有代码；进度只在内存，超时未记终态，缺防重复运行和恢复核对 |
| 上传验证 | DOM 状态、请求 200、版本变化 | 尚不能证明解压成功、阶段正确或业务流程完成 |
| 竣工阻塞诊断 | 按 BGID、变更/竣工版本聚合；联系机构或补传的经验 | 仅历史案例；缺变更记录核对和准确归因边界 |
| 文件服务 | 标准库 HTTP、回环地址、CORS | 实现存在；接收端目录端口硬编码，缺运行隔离、文件边界和数据验证 |

当前文件仅 `SKILL.md`、`reference.md` 和两个 Python 脚本。没有 README、项目约定、需求/设计/计划、测试或版本管理；本轮已补建管理框架，原始技能保持不变。

| 需求 ID | 用户任务 | 预期输出 | 优先级 |
|---|---|---|---|
| R01 | 查系统清单、版本或缺项 | 带工程/单体/单位/专业/阶段的只读快照及差异报告 | P0 |
| R02 | 对齐文件名、准备图纸 | 原件不变的暂存副本、映射清单、冲突清单、打包/验证结果 | P0 |
| R03 | 上传已有图纸新版 | 逐项目标可证明、结果可回读、支持中断核对的上传报告 | P0 |
| R04 | 初次上传或新增图纸 | 区分新增目录与更新版本，新增目标和材料经过明确规划 | P1 |
| R05 | 一般变更 | 记录/联系单/标注图和准确关联；按允许分支办理，避免全选圈图 | P0 |
| R06 | 重大变更 | 申请、重新编制图纸、说明、审查及整改各阶段清单 | P0 |
| R07 | 整改与意见回复 | 意见、目标版本、整改文件的对应关系；上传和回复分别报告 | P1 |
| R08 | 上传竣工图 | 按实际变更与项目历史分流，识别四方确认、承诺书、用章后续步骤 | P0 |
| R09 | 诊断无法完成上传 | 定位解压、缺竣工、关联、权限/阶段等原因，输出证据和处理建议 | P0 |
| R10 | 历史/缺专业/专项补录 | 补录入口与缺项计划，不冒充正常送审或已有图纸覆盖 | P1 |
| R11 | 判定变更类型、特殊工程或 BIM 需求 | 基于材料的辅助检查与待核实事项，责任主体结论另行记录 | P1 |

## 4. 关键缺口及后果

| 缺口 ID | 发现 | 后果 | 对应需求 |
|---|---|---|---|
| G01 | 技能先按图号是否有点选择技术路径，没有先识别业务阶段 | 一般变更被要求补图、重大变更被误报完成、竣工规则混用 | R05–R11 |
| G02 | 用图号首个匹配项代替稳定记录 ID | 同图号跨单体/单位/专业可能挂错记录 | R01–R04 |
| G03 | “将错就错”没有证据约束，模糊阈值被当成可靠匹配依据 | 系统错误被放大，原始本地文件失去可追溯名称 | R02、R12 |
| G04 | `.pdf/.gdb` 宣称与固定 `.pack` 辅助函数不一致 | 扩展名与内容不符，原页面前置校验可能被跳过 | R02–R04、R11 |
| G05 | 代码先置“已上传”，再发解压；HTTP 200 被当成功 | 解压失败仍被计为成功；普通网络成功掩盖业务错误 | R03、R09 |
| G06 | 超时不写结果；刷新丢内存；重试可能建新版本 | 漏项、重复上传、进度与结果数不一致 | R03、R09 |
| G07 | BGID 诊断推断过强，未纳入一般变更仅记录分支 | 把有效变更认成误圈，或用未变更内容冒充竣工成果 | R05、R08、R09 |
| G08 | 页面补丁覆盖整个旧函数，接口与全局变量无能力探测 | 系统升级后绕过新增校验或向错误阶段提交 | R03–R10 |
| G09 | 接收服务可覆盖同名文件，路径来自请求且无严格校验 | 证据丢失、目录边界不可靠、不同运行互相污染 | R01、R03、R09 |
| G10 | 上传、完成上传、完成回复、确认、签章缺少动作边界 | 技能可能扩大用户请求，或把局部成功当全过程结束 | R04–R11 |

## 5. 验收原则

1. 相同文件可以服务不同任务，但任务阶段、角色、工程范围和预期结果必须明确；无法识别时可继续只读盘点，暂停依赖这些信息的写操作。
2. 更新已有图纸必须唯一定位记录；匹配不唯一、模糊候选或元数据异常必须列入冲突，不自动挑第一个。
3. 原文件默认保留；暂存副本与原件有路径和哈希映射，改名不会改变内容。更正系统字段是另一个动作。
4. 成功必须包含本次操作的服务端回读和对应材料处理结果；流程是否结束另行记录。
5. 每项任务最终有成功、失败、待核查、跳过或未执行状态，合计与计划一致。超时、刷新、响应丢失不得直接重传。
6. 一般变更不强制新版图；重大变更上传后不宣称审查结束；BGID 异常不直接认定误圈；竣工内容由实际变更记录支持。
7. 支持部分任务执行：用户只要导出、改名计划、打包或排障，就停在对应交付，不自动推进业务。

## 6. 范围边界

本技能适合做材料盘点、系统操作编排、批量执行、验证和可追溯记录。CAD 专业重绘、工程技术审查、消防行政审批结论、各方身份确认和印章责任不由上传技能替代。已有工具能完成的打包、拆图、文件选择优先复用，人工一次多选若最直接则保留。
