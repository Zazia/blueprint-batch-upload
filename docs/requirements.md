# 需求与现状分析

日期：2026-10-09｜设计 v0.3｜按用户明确的技能定位修订，尚未实施。

## 1. 技能定位

`blueprint-batch-upload` 面向**设计单位**，接收已经准备好的成品文件，完成**初次上传、变更上传、竣工图上传**三类任务。默认结束点是执行对应页面的“完成上传”或等效上传收尾动作并确认成功；用户另有“只检查”“先不提交”等限制时遵循该限制。

“准备图纸”另设技能，承担源图命名、拆分、CAD/PDF 配对、打包和包验证。当前仅预留 [准备图纸技能设计](prepare-blueprints-design.md)，不创建或实现该技能。上传技能可直接将已打包文件按本次上传要求改名，不需要为了改外层文件名返回准备阶段。

上传阶段默认不读取、检查或同步更正包内文件；直接改包名，并把图名与改名对应关系长期保存，供二次上传复用。系统解压状态仍需核验，但不解析解压后的图纸内容。变更和竣工均支持增补与取消图纸，并同步新版目录。目录账本支持从初次上传开始建立，也支持首次接手既有项目（棕地）；棕地建档不等于历史工程业务补录。

不纳入建设单位发起变更、一般/重大变更性质判定、审图意见回复、历史工程及历史补录、系统图号/关联更正、独立 BIM 工作流、各方确认或签章。一般/重大只作为已发起变更任务的背景字段，不形成两个上传技能。

## 2. 已有能力与沿用原则

原技能已经过竣工图上传实测，优先沿用其有效经验，再补齐三类上传的共同步骤和可靠性缺口。

| 能力/经验 | 现状 | 设计处理 |
|---|---|---|
| 无点图号批量上传 | 文件图号对齐系统后，页面批量多选自动对应新版 | 保留路径 A 为首选，不要求每次重新证明已验证经验 |
| 含点图号上传 | 页面批量解析存在已知问题 | 保留路径 B 逐条上传新版，初次上传尽早预检图号中的点 |
| “将错就错”对齐 | 已有目录以系统图号为匹配基准 | 保留；确认对应图纸后改成品文件名，不擅改系统目录 |
| JS 注入与页面修复 | 已有 CORS 服务、上传函数及 DOM/jQuery 修复 | 优先复用；页面必要字段/函数不兼容时才停下定位差异 |
| 分段循环 | 浏览器内按段顺序上传，避免每文件反复驱动 | 保留，补日志、超时结果和断点核对 |
| 竣工必传规则 | 曾被发起变更勾选的图纸，即使没有变更新版，也需要上传竣工新版才能通过上传收尾校验 | 作为默认执行规则；不以“没有变更版”排除必传项 |
| 完成上传 | 原参考记录了竣工校验和提交链路 | 纳入任务闭环，不止于文件传完 |

资料来源和用户确认的优先级见 [sources.md](sources.md)。遵循经验不等于忽略实际报错；读到明确页面差异时保留证据并针对性调整，不开展无必要的全流程重新调研。

## 3. 需求范围

本版重排需求编号，旧 v0.1 编号保留于 Git 历史。

| ID | 需求 | 验收结果 |
|---|---|---|
| R01 | 识别三类上传及设计单位上下文 | 工程、单位、单体、专业和阶段明确，操作本单位任务 |
| R02 | 初次上传前检查成品格式与命名 | 类型、非空、重名、图号中的点、文件名结构等问题在建目录前处理 |
| R03 | 按上传要求改名成品文件 | 不读包内；长期保存图名/原名/上传名映射，后续同范围同图名直接复用，无冲突、无覆盖 |
| R04 | 初次上传 | 批量建立图纸记录及首版，记录与文件一致，不重复建目录 |
| R05 | 变更上传 | 处理已有图新版、增补、取消及相关目录材料，完成上传 |
| R06 | 竣工图上传 | 处理已有图新版、增补、取消及目录；覆盖尚缺本阶段有效上传结果的曾勾选图纸 |
| R07 | 复用路径 A/B | 无点批量、含点逐条；分段执行，保留既有修复经验 |
| R08 | 上传核验与恢复 | 保存和解压结果核验，进度持久化，结果未知先回读再重试 |
| R09 | 完成上传与阻塞定位 | 完成对应上传节点并确认；受阻时具体定位缺图、解压或其他校验问题 |
| R10 | 与准备图纸技能衔接 | 接收成品目录和可选清单即可，不强依赖另一个技能已安装 |
| R11 | 长期目录账本与初次/棕地建档 | 从系统建立真实已知基线，身份/版本/状态可追溯，不将本次文件夹当完整目录 |
| R12 | 增补图纸 | 明确增补项点击“上传图纸”补充，保存新 BPID，核对新版目录 |
| R13 | 取消图纸 | 对原图上传取消变更单，保留 BPID/版本；不点击物理删除，核对新版目录 |
| R14 | 目录与取消材料缺项提示 | 缺新版目录或相应取消变更单时，提醒具体材料及范围，不把机器账本当正式目录 |
| R15 | 跨任务目录恢复与变更追踪 | 改名规则可重放，系统外部修改可对账，收尾失败保留上传事实和未提交修订 |

## 5. 完成标准

1. 初次上传和增补：文件与新增记录/首版对应；更新和取消：文件与原 BPID 对应。明确新增与匹配失败分开，不产生错误记录。
2. 初次上传尽早发现图号含点，优先采用不含点的命名；已有系统图号含点时保留对应关系并走路径 B。
3. 竣工必传集合按曾勾选状态确定，无变更新版不是豁免理由。接口 BGID 是现有已验证识别入口，已知勾选记录也不能漏掉。
4. 全部所需文件的保存、版本和解压结果已核验；缺文件必须列出，不能靠删除关联减少应传集合。
5. 对应范围的“完成上传”成功。文件全部传完但收尾失败，应报告“文件已上传，完成上传受阻”，不能宣称任务完成。
6. 不把完成上传等同于全部审查通过或竣工编制全流程完成；该技能负责设计单位上传节点。
7. 新版目录和取消变更单按本次增补/取消逐项管理，缺失须明确提醒。取消不清 BGID，也不能从账本删行后就视为满足竣工校验。
8. 改名映射跨阶段复用；棕地采集从当前系统开始，保留来源和缺失范围，不要求读取包内或重建不可得的全部历史。
