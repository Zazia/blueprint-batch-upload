# blueprint-batch-upload 技能完善设计

日期：2026-10-09｜设计稿 v0.2｜设计单位上传技能｜尚未实施

本版按用户明确定位收窄范围，取代 v0.1 的全过程设计。需求见 [requirements.md](requirements.md)，经验与资料见 [sources.md](sources.md)，实施任务见 [tasks.md](tasks.md)。前置技能单独预留在 [准备图纸技能设计](prepare-blueprints-design.md)。拟议模块尚未实现。

## 1. 目标与边界

设计单位提供已经准备好的 PACK 或允许直接上传的 PDF 等成品文件，技能完成初次上传、变更上传、竣工图上传，并执行对应页面的“完成上传”或等效上传收尾动作，回读确认成功。

三类任务只有两种核心文件操作：**初次上传建立目录及首版；变更和竣工上传对应已有目录上传新版。** 二者共享上下文识别、成品检查、上传改名、执行、验证和恢复。变更与竣工的区别主要在任务入口、阶段和必须上传的图纸集合，不需要各写一套传输引擎。

源图命名、拆图、配对、打包由“准备图纸”技能承担。本技能可以直接按上传要求改名已打包文件，不拆包、改图或重新打包。不包含历史工程、历史补录、建设单位发起申请、变更分类判定、审查回复、各方确认和签章。

## 2. 沿用原技能的执行经验

以原技能实测经验和本次用户确认为默认规则：

| 规则 | 执行方式 |
|---|---|
| 页面批量上传能按图号对应已有记录 | 对齐系统图号后，优先路径 A 批量多选上传 |
| 图号含点存在批量识别问题 | 含点文件走路径 B，逐条对应已有图纸上传新版 |
| 系统目录可能存在录入差异 | 确认图纸对应关系后以系统现有图号改成品文件名，保留“将错就错”策略 |
| 页面上传函数存在已知 DOM/jQuery 问题 | 保留原修复方案和 CORS 文件服务的作用，补必要上下文检查 |
| 浏览器内分段循环已经可用 | 保留每段约 15–20 项的起始配置，按实际体积/耗时调整，补持久化恢复 |
| 变更勾选状态影响竣工提交 | 曾勾选图纸不论有没有变更版，都必须具备竣工新版才能完成上传 |
| 完成上传有服务器校验 | 沿用已记录的校验/提交链路及错误诊断，不以文件传完为结束 |

正常执行不要求重新论证以上经验。只检查当前登录工程、阶段、必要页面对象和返回结构；发现实际不兼容时再针对差异调整。既有体验不因改进日志或代码组织而被推翻，也不把历史经验表述成本轮重新做过在线测试。

## 3. 三类上传流程

### 3.1 共有入口

从用户信息及页面读取：上传类型、工程/WID、业务记录/WHID、设计单位/OrgId、单体、专业、成品目录、当前阶段、用户约定的范围。WHID 与页面单体字段分别保存原始值，不凭名称猜测两者含义。上传时选择具体单体；“所有”仅可用于盘点。

默认目标是完成上传。仅当用户明确要求试传、只检查、只传一部分或先不点完成时，才停在该指定节点。不要在已授权完整上传任务的末尾再重复询问是否点击“完成上传”。

### 3.2 初次上传

前置条件：设计单位的工程上传任务已经存在，单体、专业等已具备可选入口，文件已由前置阶段准备完成。

1. 扫描成品文件：实际文件类型、非空、可读、命名结构、重复图号、大小写/全半角冲突、禁止文件名字符及图号中的点。初次上传的预检应尽量把问题解决在创建系统目录之前。
2. 优先采用 `图号_图名.pack` 等系统可识别形式。**图号尽量不用点**，推荐采用不冲突的连字符等规则；文件扩展名前的点不是图号中的点。
3. 成品文件外层命名可直接调整。若图号修改影响包内图签、目录或已确定的正式图号，列出内外不一致，交前置准备阶段处理内容或使用明确的上传别名映射；不得声称只改外层文件名就已更正包内内容。点号不是格式违法判定，不直接全局替换所有点。
4. 检查系统当前范围是否已有部分记录，防止“初次上传中断后重跑”重复建目录。只对确需新增的文件使用原生批量上传入口，保存返回的新 BPID/版本。
5. 核验记录数量、图号图名、专业单体和文件/解压结果，完成页面上传节点并回读结果。

初次上传的新增入口与已有图纸上传新版不同，不把原逐条上传新版函数套到不存在的图纸上。原则上用原生批量路径即可；若初次上传图号必须保留点，先处理该具体命名例外，不能误用“已有 BPID”的路径 B。

### 3.3 变更上传

前置条件：建设单位已发起变更并推送设计单位；本技能进入该既有任务，不负责发起、选定一般/重大性质或圈选图纸。

1. 进入设计单位图纸变更上传页面，读取当前任务、阶段及系统已有关联图纸。
2. 将本次成品文件对应到本单位、单体、专业内已有图纸；以系统图号为准改文件名。
3. 无点图号走路径 A，含点图号走路径 B；使用当前变更阶段上传新版，不能套用竣工阶段值。
4. 上传用户提供且本任务要求的变更说明等材料（如该页面要求），只处理成品上传，不编制说明或判定变更性质。
5. 验证所有本次所需图纸与材料，再执行“完成上传”并回读成功。

一般/重大是既有任务的背景属性，两者共用上传流程。完成后即便系统进入待审查，设计单位“完成上传”任务仍已完成。发现文件找不到原图时输出未匹配项，不自动创建新目录；不另设“变更中新建图纸”模式，确有此需求时再作明确扩展。

### 3.4 竣工图上传

前置条件：竣工图任务已推送到设计单位，用户提供相应成品文件。

1. 读取该上传任务覆盖的各单体、专业图纸和版本；通过原始接口响应获取 BGID，不能只看页面文字或是否出现变更版本。
2. 形成应传集合：**凡曾在发起变更时被勾选的图纸，不论是否上传过变更新版，都要具备竣工新版。** 已有可确认有效竣工版的图纸无需无意义重复上传；如本次另有更新文件则按新任务上传。
3. 对尚缺竣工版的必传图逐项寻找成品文件。没有变更版、实际内容未变、用户当前目录里没有该文件，都不能成为从应传集合移除它的理由。
4. 以已有系统图号改名成品，复用路径 A/B 上传到原 BPID，使用当前竣工阶段，核验竣工版本和解压结果。
5. 全量复查必传集合已补齐，再执行“完成上传”；如提示仍有变更图纸未上传竣工图，按 BGID 与竣工版差集列出具体缺项，补齐后重试收尾。

原经验中“按现行批准版补传竣工版”保留为缺文件时的候选处理：已有文件经确认就是所需竣工内容时，可用对应文件补传；否则给出缺文件清单，交用户或前置准备阶段提供。技能不清 BGID、不删除关联来规避校验，也不把“无变更版”解释为无需上传。

## 4. 两技能的接口与改名边界

| 工作 | 准备图纸技能 | 本上传技能 |
|---|---|---|
| 源 CAD/PDF 的规范命名、图号与内容一致 | 负责 | 报告发现的不一致 |
| CAD 拆图、PDF 拆分、配对、T3/内容检查 | 负责 | 不拆图或修改图内内容 |
| ZwPack 打包与包验证 | 负责 | 接收成品及可选验证结果，发现无效包返回缺项 |
| 已打包文件按新上传命名规则改名 | 可在交付前处理 | 可直接处理 |
| 已打包文件按已有系统图号改名 | 无须提前拥有系统目录 | 负责，保留名称映射 |
| 页面上传、结果核验、完成上传 | 不负责 | 负责 |

最小输入是成品目录及工程/单体/专业归属。可选 `prepared-manifest.json` 提供文件原名、原图号/图名、成品路径、类型、大小、哈希、配对来源及验证结果。无清单也能工作，不要求先安装或调用准备技能。

直接改名仅作用于本次指定的成品目录，先生成无冲突映射，再执行并记录；不要求用户为了每次改名另走准备技能或逐文件确认。用户要求保留原名时使用上传副本。修改前检查目标重名、文件占用、循环改名和规范化碰撞，必要时中间名过渡；改名前后内容哈希必须一致。改名不改包内内容，也不修改系统现有图号。

## 5. 匹配与上传方式

### 5.1 已有图纸对应规则

限定工程、设计单位、单体、专业和阶段后，优先图号精确匹配，再图名核对。沿用原技能多轮匹配和 0.75 相似度经验生成候选；重号、近似名称或多个文件对应同一记录时单列复核，不随意取首项。匹配成立后保存 BPID，后续上传和核验都绑定同一记录。

系统图号录错但图纸对应关系清楚时，按原经验使用系统图号命名成品文件，不擅自修正系统目录。文件名中的原图号、系统图号与 BPID 一并留档。

### 5.2 路径选择

| 场景 | 方式 |
|---|---|
| 初次上传，命名格式已检查 | 原生批量上传，新增目录及首版 |
| 变更/竣工，无点且已对齐系统图号 | 路径 A：页面批量多选自动对应新版，首选 |
| 变更/竣工，图号含点 | 路径 B：原 CORS + JS 注入方式，对应已有图纸上传新版 |
| 变更/竣工，需要全自动且原生多选工具不可用 | 沿用路径 B 的分段循环 |
| 原生选择需要人工一次多选 | 提供明确目录与文件集合，人工选择后继续验证和完成上传 |

混合文件先 A 后 B。人工一次多选是可用的直接路径，不为消除一次简单人工操作重造上传系统。若当前工具能直接设置原生文件输入，可在原流程内使用，但不以重新研究工具能力为每次任务的前置阶段。

## 6. 数据、执行与恢复

### 6.1 最小持久化记录

| 对象 | 内容 |
|---|---|
| 任务上下文 | runId、上传类型、工程/单位/单体/专业、当前阶段、任务范围及用户限制 |
| 系统快照 | BPID、图号图名、BGID/已知勾选信息、版本和 VSID、快照范围完整性 |
| 文件与改名表 | 原名、上传名、路径、大小、哈希、对应 BPID（初次上传后回填） |
| 上传计划 | 应传集合、已满足项、待上传项、缺文件、未匹配及冲突、路径 A/B |
| 执行结果 | 每项状态、实际版本、解压结果、错误、重试/恢复记录 |
| 收尾结果 | 校验响应、完成上传响应、回读状态、剩余阻塞 |

使用 `runs/<runId>/` 下 JSON/JSONL 和报告即可，运行资料不进 Git。采集覆盖任务范围并绑定原请求的专业/单体，避免晚到响应串数据；分页、缺 BGID 或缺版本时标明不完整，不把未知集合当空集合。

### 6.2 保留分段循环，补齐结果

保留浏览器内顺序队列和原上传修复逻辑；每段启动后短轮询，不逐文件反复发指令。每项写入持久化结果，超时也必须有记录。运行锁防止覆盖同一批次；切换专业、阶段或登录失效时暂停派发新任务。

文件状态：`planned → uploading → version_saved → processing → verified`。无需解压的合法 PDF 可跳过 processing。失败为 failed，响应丢失或超时为 unknown，未派发/缺件为 blocked 或 planned。所有状态计数与计划一致。

### 6.3 验证与恢复

- 核对本次文件的存储和版本业务响应、目标 BPID、实际 VSID/版本、阶段及后处理结果。请求 200 或行内“已上传”不能单独代表解压完成。
- 版本数增加是原技能的正常观察指标；仍保存实际返回标识，避免同阶段更新或替换造成误判。
- 超时、断网、刷新后先查服务端是否已经保存；已成功则补记结果，不立即重传制造新版本。初次上传同样先找已建目录。
- 解压失败单独定位；先检查已有版本的处理结果，再决定是否重传，不无限重试相同错误。
- 合法 PDF 等材料保留真实扩展名和原生校验，不沿用辅助函数固定 `.pack` 的做法。

### 6.4 本地服务的有限改进

保留两个标准库服务，参数化目录和端口。只提供本次文件，接收端只写本次运行目录；校验文件标识及解析后的路径，防止 Windows 盘符/分隔符越界，证据文件不覆盖。绑定回环地址，限定实际站点和运行访问范围，任务结束停止服务。无需引入数据库、常驻守护程序或管理网页。

## 7. “完成上传”的闭环

完成上传是默认任务的一部分，文件全部核验后继续执行，不能默认只交付“已上传文件清单”。

1. 核对本次任务所有必传图纸和材料，不仅检查本地目录中实际存在的文件。竣工尤其检查曾勾选图纸的竣工版差集。
2. 执行当前页面的上传校验与“完成上传”或等效动作。竣工沿用原经验：`checkCanSealJGT` 校验后调用 `blueprint_uploadComplete_jgt`；页面按钮已封装时优先遵循页面顺序。初次/变更使用其各自上传节点，实施时补齐实际入口，不能一律照搬竣工接口。
3. 读取响应并回读状态。一般变更可能显示已完成变更，重大变更可能进入待审查；两者均应以设计单位上传节点已成功提交为完成依据。
4. 失败时输出明确缺项/错误，能在原授权范围内处理的继续补齐再提交。若缺少成品或需其他责任人操作，报告阻塞及剩余动作。

如果当前页面要求确认或签章等外部前置，列明具体阻塞，不替他人完成责任确认。用户限定只试传或部分上传时，不点击会结束整个任务范围的收尾按钮。

完成报告给出：三类上传中的哪一类、范围、改名和匹配数量、成功/失败/缺件/待核查数量、完成上传是否成功及证据。完成设计单位上传不等于审查通过，也不等于四方确认及整个竣工编制流程结束。

## 8. 目标文件组织

后续实施按需建立，当前不创建占位代码：

```text
SKILL.md                    设计单位、三类上传、默认完成上传、路径选择
reference.md                保留原经验与相对引用，逐步整理公共技术内容
references/
  initial-upload.md         初次格式/命名检查、新增目录、上传收尾
  change-upload.md          已发起变更任务中的对应新版上传
  completion-upload.md      竣工必传集合、BGID、完成上传排障
  matching-and-renaming.md  成品对应与直接改名
scripts/
  cors_server.py            保留并参数化限定服务范围
  receive_server.py         参数化和证据持久化
  upload_plan.py            成品预检、对应、改名及差集
  browser/                  需要复用时抽出采集、上传、核验脚本
```

不在本技能添加拆图/打包模块、变更申请/判定模块、历史补录模块。准备图纸技能的预留文档只属于开发设计材料，不成为上传任务的必读执行文档。

## 9. 实施顺序与验收

先保留竣工已验证链路并补齐必传差集和完成上传闭环，再复用对应新版能力补变更入口，补初次上传命名预检与新增入口，最后整合恢复与文档。三类上传均是本版核心范围，不再将初次上传降为可选扩展。

验证重点是新增部分与真实缺口：初次点号/冲突预检、成品改名内容不变、变更/竣工对应原记录、曾勾选但无变更版仍必传、解压终态、超时恢复和完成上传。既有竣工案例作为回归基线，不要求每次任务重新证明全套经验。具体验收见 [tasks.md](tasks.md)。
