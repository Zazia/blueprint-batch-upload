## 2. 本版设计的取用原则

新增 U1：用户于 2026-10-09 在本对话明确确认技能角色、范围、完成目标及原技能经验。U1 是本版设计需求依据，不修改原始资料内容，也不将设计决定表述为法规更新。

- 角色固定设计单位，任务为初次、变更、竣工三类上传，默认完成上传。
- 准备图纸另设技能，本上传技能可直接改名已打包文件。
- 原技能已经过竣工图上传检验，优先相信并沿用有效经验；正常执行不重复论证。
- 曾在发起变更时勾选的图纸，不论有没有变更新版，都需具备竣工新版才能通过上传收尾。这是本版默认执行规则，不再列为待重新证明的假设。
- 历史工程、历史补录不纳入本技能。

执行设计以 U1 明确范围及确认经验为准，C1/C2 提供具体上传路径和排障方法，S1–S6 提供格式与阶段背景。手册的宏观业务描述不用于推翻已验证的系统上传限制；读到明确的新页面差异时再定位适配，不假设系统已经改变。

### 3.1 资料差异的处理

| ID | 差异或限制 | 本版决定 |
|---|---|---|
| D01 | S3 允许建设单位自行上传或某些一般变更无需新版图 | 仅作流程背景；本技能处理已经到设计单位的上传任务，不扩展建设单位模式或变更性质判定 |
| D02 | 手册强调图号图名一致，原实测批量匹配认系统图号 | 优先沿用原经验对齐图号，并核对图名避免错配；不把每次重测匹配机制设为前置条件 |
| D03 | 原经验指出含点识别失败 | 保留默认分流，不要求先再试一次批量来证明错误；初次从命名上尽早避免 |
| D04 | 版本通常增加，旧代码也处理同版本记录 | 保留版本变化检查，同时使用实际 VSID/响应核验，避免日志误判 |
| D05 | v0.1 将 BGID 规则列为待重新验证，并强调查真实变更 | 按 U1 修正：系统必传依据曾勾选，是否有变更新版不改变这一要求 |
| D06 | 原参考记录后台清 BGID 和补传两条修复建议 | 本版设计单位上传任务以补齐应传文件为路径，不提供清关联功能；缺成品具体列出 |
| D07 | 原参考可按现行批准版补传 | 保留候选路径；所用文件须确为需要提交的内容，不能仅靠改状态推断内容正确 |
| D08 | 当前 BGID 不一定表达全部历史圈选过程 | 以 BGID 识别已知必传项，结合可得任务/勾选信息和服务端缺项；缺字段不能视作从未勾选，不要求先重建完整变更历史 |
